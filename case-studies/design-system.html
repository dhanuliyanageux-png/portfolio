Founding a design system three squads actually use

Three teams, three button components, zero shared language. I built the system — and the process around it — that got everyone contributing instead of forking.

Role
Design systems lead
Responsibilities
Tokens, component design, docs, contribution model, adoption
Team
2 designers (part-time), 3 engineers, design-ops
Timeline
2024 · ongoing, first 6 months covered here

The challenge

Rapid team growth left the product visually fragmented — inconsistent spacing, four shades of “primary blue,” and accessibility regressions shipping unnoticed. Every squad rebuilt the same components slightly differently, and design-to-dev handoff meant re-specifying things that should have been settled once.

Approach

I treated adoption as the actual deliverable. A perfect library nobody uses is a failure. So the work ran on three tracks in parallel:

  • Foundations first. A token layer (color, type, space, radius, elevation) mapped 1:1 between Figma and code.
  • Migrate the highest-traffic components — button, input, select, modal, table — with real usage audited from production.
  • A contribution model so squads could propose and land changes without a bottleneck.

The system only works if contributing to it is easier than working around it.

Documentation

Each component page covers anatomy, variants, states, content guidelines, accessibility notes, and a live code sample. Written for the person reaching for it at 4pm, not for a design-system connoisseur.

Impact

120+Components adopted across 3 squads
−40%Design-to-dev handoff cycle time
0Net-new contrast failures since launch

What I'd do differently: I documented governance too late. For the first two months “who decides” was ambiguous and a few changes stalled. Writing that down early would have saved weeks.
