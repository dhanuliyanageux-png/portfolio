Rebuilding Skapp's design system, component by component

Skapp replaces the seven-to-ten separate tools a growing team would otherwise stitch together — project management, people management, time tracking, time-off, e-signatures, invoicing — with one platform. That range is exactly what makes its design system hard: a kanban board, an org chart, a signature flow and an invoice all have to feel like the same product. As Lead UX Designer, I owned that system end to end and rebuilt it from the component level up, in Figma and in code, with the team who'd actually use it.

01 · ProblemOne platform, six modules, and a single product feel

Skapp's whole pitch is consolidation: instead of running a separate project tool, HR system, time tracker, e-signature app and invoicing tool, a team runs one platform. That's a great pitch for the person buying the software. It's a hard brief for the person designing it, because it means Skapp's own product has to cover kanban boards and Scrum flows, org charts and employee profiles, clock-in time tracking, leave calendars, legally-binding signature flows, and invoices tied to logged hours — all under one roof, all expected to feel like the same product.

A design system for something that wide can't be a button and a color palette bolted on afterward. It has to hold together across project-management-flavoured screens, HR-flavoured screens, and finance-flavoured screens without each one quietly drifting into its own dialect.

02 · AuditBefore rebuilding anything, I catalogued what actually existed

By the time I took ownership, Skapp had grown the way most fast-moving products do: components got built for the screen in front of a designer that week, not for reuse, and the gap between what Figma said and what shipped in code widened with every sprint. Before rebuilding anything, I spent time cataloguing what actually existed — walking every screen across Project, People, Time Tracking, Time-off, E-signatures and Invoicing, and pulling out every variant of every component I found along the way.

None of it was wrong exactly — each screen had made sense in isolation at the time it was built. The audit wasn't about assigning blame for that; it was about having a real inventory to rebuild from, instead of guessing at what "the button" or "the filter" was supposed to look like. That prioritised the rebuild: start with whatever showed up most often across the audit, since that's where the inconsistency was doing the most visible damage.

03 · FoundationsFoundations first, in three tiers of tokens

Before touching a single component, I rebuilt the foundations: color, type, spacing, radius and elevation, defined once as tokens and mapped as Figma variables. I structured them in three tiers rather than one flat list. Global tokens held the raw palette and scale — values with no opinion about where they'd be used. Semantic tokens gave those values a role, like color-action-primary or space-comfortable. Component tokens then pointed at a semantic token for one specific job, like a button's background.

The extra layer looks like overhead until you need to re-theme something: change what color-action-primary points to, and every semantic and component token built on it follows automatically — nobody has to go and edit the button.

Decision · How should the tokens be structured?

The alternative

One flat list of tokens

Simpler to read, but every component would carry its own raw value, so re-theming something means editing each component by hand.

Chosen

Three tiers: global, semantic, component

Raw values hold no opinion, semantic tokens give them a role, component tokens use that role for one job. Change what color-action-primary points to and everything built on it follows.

That's the token system's job done at the scale of a single value. The same mechanism plays out at the scale of a whole component: every button on the product reads from the same component token, so one change moves everywhere that token is used at once.

04 · ComponentsRebuilding the library from the atoms up, with one dependency rule

With foundations in place, I rebuilt the components themselves from the atoms up — inputs, buttons, table rows, avatars, badges — auditing each one against how it actually got used across Project, People, Time Tracking and Invoicing, not how it was originally invented in isolation for a single screen. Variants and states that turned out to be one-offs got folded back into the closest real pattern; ones that were genuinely different got documented as their own thing instead of a lookalike that quietly behaved differently.

I kept the library to one rule: each layer only depends on the layer below it, never sideways. Primitives — an icon, a badge, an avatar — are the smallest reusable pieces. Components are built from primitives: a table row is an avatar, two text styles and a badge, composed once and reused everywhere a row appears. Patterns are built from components: a data table is table rows plus a header plus pagination. A pattern can reach down into components; two components never quietly depend on each other.

In Figma, that meant splitting the single sprawling file I inherited into three published libraries — Foundations, Components and Patterns — each versioned on its own and consumed downstream. A product file always pulled from a known, published source instead of a local copy someone had detached and started editing in place, which was the single biggest cause of the drift I'd catalogued in the audit.

05 · GovernanceDocumentation and a contribution model, so the system scales past one person

Documentation as a first-class deliverable

"From Figma level to documentation level" was the brief, and I treated documentation as part of the component, not an afterthought once it shipped. Every component's doc page covered its anatomy, its variants and states, content guidelines, accessibility notes, and a live reference — written for whoever was reaching for it under deadline, not for a design-system connoisseur reading it cover to cover.

A contribution model, not a bottleneck

A system this wide can't be maintained by one person reviewing every pixel. The part of the job that mattered as much as the components themselves was the process around them: a way for anyone on the team to request a pattern, get it checked against what already existed, and — if it really was new — design, build and document it without waiting in a queue behind me.

06 · MaintenanceKeeping it alive, every release

A design system that stops changing the day it launches is already dying. Maintaining Skapp's meant a few unglamorous habits, kept up every release rather than revisited once a quarter:

  • Version every library change. A breaking update to a component never landed on a product file unannounced — squads could see what changed and choose when to pull it in, instead of finding out from a broken screen.
  • Deprecate with a path, not a warning. A component that had been superseded got marked deprecated alongside the component that replaced it and a note on how to migrate — never just "do not use," which only tells someone what to avoid, not what to do instead.
  • Treat Figma and code as out of sync the moment either one changes, not months later when someone finally notices the documentation screenshot doesn't match what shipped. That's the same discipline the audit was built to catch in the first place — just applied continuously instead of once.

None of that is glamorous work, but skipping it is exactly how a system ends up needing to be rebuilt from scratch a second time.

07 · OutcomeScope and durability, not a single number

This wasn't a project with a single conversion number to report — it was infrastructure, owned and maintained over time rather than shipped once. The honest measure of it is scope and durability, not a before/after metric invented to fill a slide.

What I took from it

  • The governance model is as much the deliverable as the components. A library nobody outside me could contribute to would have stopped scaling the moment the product did.
  • Reuse has to be the easy path, not a rule someone has to remember. Checking the library before designing anything new is what actually kept the system from sprawling — not a guideline saying to check it.
  • A system this wide only holds together at the foundation level. Trying to keep a kanban board, a signature flow and an invoice consistent screen-by-screen would never have worked; keeping their tokens consistent did.
